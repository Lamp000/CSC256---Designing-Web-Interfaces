For a class project like this, client-side storage is completely reasonable, and you can keep the architecture fairly simple. You do not need a real backend unless your rubric specifically requires one.

A good setup would be:

HTML/CSS/JavaScript

localStorage for saving the user's game collection and playlists

A small hard-coded catalog of video games and board games, or data loaded from a JSON file

Cards, cover art, search/filtering, and playlist screens to give it the Spotify-like feel

Your stored data could look roughly like this:

const collection = [
  {
    id: 1,
    title: "Hades",
    type: "video-game",
    cover: "images/hades.jpg",
    genre: "Roguelike"
  },
  {
    id: 2,
    title: "Catan",
    type: "board-game",
    cover: "images/catan.jpg",
    genre: "Strategy"
  }
];

const playlists = [
  {
    id: 1,
    name: "Game Night",
    games: [2]
  },
  {
    id: 2,
    name: "Favorites",
    games: [1, 2]
  }
];

localStorage.setItem("collection", JSON.stringify(collection));
localStorage.setItem("playlists", JSON.stringify(playlists));

Then whenever the site loads:

const collection =
  JSON.parse(localStorage.getItem("collection")) || [];

const playlists =
  JSON.parse(localStorage.getItem("playlists")) || [];

That means a user can add something to their collection, refresh the browser, and it will still be there. That is probably the most visible way to demonstrate client-side data storage during your presentation.

I would structure the site around four main views: Home, Browse, My Collection, and Playlists. Browse could show a grid of game covers with an Add to Collection button. My Collection would only show saved games. Playlists could let the user create a playlist, name it, and add games from their collection.

For example:

function addToCollection(game) {
  const collection =
    JSON.parse(localStorage.getItem("collection")) || [];

  const alreadyAdded = collection.some(item => item.id === game.id);

  if (!alreadyAdded) {
    collection.push(game);
    localStorage.setItem("collection", JSON.stringify(collection));
  }
}

And creating a playlist could be as simple as:

function createPlaylist(name) {
  const playlists =
    JSON.parse(localStorage.getItem("playlists")) || [];

  const playlist = {
    id: Date.now(),
    name: name,
    games: []
  };

  playlists.push(playlist);

  localStorage.setItem("playlists", JSON.stringify(playlists));
}

For the presentation, I would prioritize visual polish over complicated functionality. A dark interface, large cover images, a left navigation sidebar, horizontal sections such as "Recently Added" or "Popular Games," hover effects, and a clean playlist page will make the project feel much more complete even if the underlying JavaScript is relatively straightforward.

You also have a nice opportunity to make the Spotify concept fit games instead of copying it literally. For example, playlists could be things like "Friday Game Night," "Games to Finish," "Co-op With Friends," "Quick Board Games," or "Favorites." That makes the playlist concept make sense for both video games and board games.

One important distinction: I would use localStorage rather than sessionStorage. sessionStorage disappears when the browser tab/session ends, while localStorage stays saved, which makes the collection feature much more convincing.

If your professor mainly wants evidence that you understand client-side data, this is enough to demonstrate a complete flow:

Browse game → Add to collection → Save to localStorage → Create playlist → Add collection item to playlist → Refresh page → Data remains.

That gives you a manageable final project without needing authentication, databases, servers, or a full Spotify-scale application.

## Response:

Correct — you generally should not store the actual images in localStorage.

localStorage is relatively small (commonly around 5–10 MB per origin, depending on the browser), and images converted to Base64 become even larger. A collection of game covers would fill it quickly.

Instead, store references to images:

{
  id: 1,
  title: "Hades",
  type: "video-game",
  image: "images/hades.jpg"
}

Then your project might look like:

project/
├── index.html
├── css/
│   └── style.css
├── js/
│   └── app.js
└── images/
    ├── hades.jpg
    ├── minecraft.jpg
    ├── catan.jpg
    └── wingspan.jpg

The JPG/PNG/WebP files live normally in your project's images folder. localStorage only stores the tiny string "images/hades.jpg".

So your saved collection could be:

[
  {
    "id": 1,
    "title": "Hades",
    "image": "images/hades.jpg"
  },
  {
    "id": 7,
    "title": "Catan",
    "image": "images/catan.jpg"
  }
]

That's very small. Even hundreds of games wouldn't be a problem if you're only storing metadata such as IDs, titles, genres, image paths, ratings, and playlist membership.

If users upload their own images

That's where I'd change approaches. If your app lets the user choose an image file from their computer and expects that image to persist, IndexedDB is much better suited than localStorage.

But if you're supplying the game covers yourself, I wouldn't bother. Keep the images as files and use localStorage for things like:

Collection
    ↓
Game IDs

Playlists
    ↓
Playlist name + Game IDs

Favorites
    ↓
Game IDs

User preferences
    ↓
Theme, sorting, etc.

For a web-design final, this is actually a nice architecture because you can have 50+ game covers and make the application look substantial without putting 50 images into browser storage.

You could also have a games.json containing your entire catalog, while localStorage only remembers which games the user selected. That's probably the approach I'd recommend for your project.

This code is basically setting up a small database inside the user's browser called GameLibrary. I'll go through it piece by piece.

const request = indexedDB.open("GameLibrary", 1);

This tells the browser:

Open an IndexedDB database called "GameLibrary", using version 1.

If the database doesn't exist yet, the browser creates it.

request represents the process of opening/creating that database. IndexedDB operations happen asynchronously, so JavaScript doesn't immediately give you the database.

onupgradeneeded

request.onupgradeneeded = function (event) {

This function runs when the database needs to be created or upgraded.

For example, the first time you visit your website:

Does "GameLibrary" exist?
        │
        └── No
             │
             ▼
      onupgradeneeded runs

If you refresh afterward, the database already exists at version 1, so this function normally won't run again.

Getting the database

const db = event.target.result;

This gives you the actual database that was just opened.

You put it into a variable called db so you can work with it:

db

essentially means:

My GameLibrary database.

Checking for "games"

if (!db.objectStoreNames.contains("games")) {

An object store is IndexedDB's rough equivalent of a database table.

So you can think of the database like:

GameLibrary
│
├── games
│
├── playlists
│
└── maybe something else later

This line asks:

Does the database NOT already have an object store called "games"?

The ! means not.

If "games" doesn't exist, the code inside the if executes.

Creating the games store

db.createObjectStore("games", {
    keyPath: "id",
    autoIncrement: true
});

This creates the "games" object store.

The interesting part is:

keyPath: "id"

That says every game will be identified by its id.

And:

autoIncrement: true

means IndexedDB will automatically generate those IDs for you.

So suppose you add:

{
    title: "Hades",
    genre: "Roguelike"

    id: 2,

GameLibrary

The important difference from a normal SQL database is that IndexedDB stores JavaScript objects, so your objects don't all have to fit rigid columns like that table implies.

Yes, but I’d split it into a few functions rather than put everything into one giant function.

A clean setup would be:

let db;

// 1. Open/create the database
function openDatabase() {
  const request = indexedDB.open("GameLibrary", 1);

  request.onupgradeneeded = function (event) {
    db = event.target.result;

    if (!db.objectStoreNames.contains("games")) {
      db.createObjectStore("games", {
        keyPath: "id",
        autoIncrement: true
      });
    }
  };

  request.onsuccess = function (event) {
    db = event.target.result;

    // Once database is ready, display saved games
    loadGames();
  };

  request.onerror = function () {
    console.log("Database failed to open");
  };
}

Then have a separate function for adding a game:

function addGame() {
  const game = {
    title: titleInput.value,
    type: typeInput.value,
    image: imageInput.files[0]
  };

  const transaction = db.transaction("games", "readwrite");
  const store = transaction.objectStore("games");

  store.add(game);
}

And another function for retrieving them:

function loadGames() {
  const transaction = db.transaction("games", "readonly");
  const store = transaction.objectStore("games");

  const request = store.getAll();

  request.onsuccess = function () {
    const games = request.result;

    games.forEach(function (game) {
      displayGame(game);
    });
  };
}

Then another function handles just displaying one game:

function displayGame(game) {
  const card = document.createElement("div");

  const title = document.createElement("h3");
  title.textContent = game.title;

  const img = document.createElement("img");

  if (game.image) {
    img.src = URL.createObjectURL(game.image);
  }

  card.appendChild(img);
  card.appendChild(title);

  document.querySelector("#gameCollection").appendChild(card);
}

And when your page first loads:

openDatabase();

So conceptually, you're separating responsibilities:

openDatabase()
    ↓
Sets up IndexedDB
    ↓
loadGames()
    ↓
Gets previously saved games
    ↓
displayGame()
    ↓
Puts them on the webpage

User submits form
    ↓
addGame()
    ↓
Saves new game to IndexedDB

This is much easier to work with than something like:

function doEverything() {
  // 150 lines of database,
  // form, image, and HTML code
}

One particularly important detail is the global:

let db;

You put that outside your functions because multiple functions need access to the database.

Then later:

request.onsuccess = function (event) {
  db = event.target.result;
};

stores the opened database into it.

That way addGame() can later do:

db.transaction(...)

without having to reopen the database every time.

For your project, I’d probably aim for roughly these functions:

openDatabase()
addGame()
loadGames()
displayGame()
deleteGame()

Then later, when you implement playlists, you can add playlist-specific functions. This structure is simple enough for a class project but also gives you something well organized to explain if your instructor asks how your JavaScript works.

No — loadGames() itself does not create duplicates in IndexedDB. It only reads the games that are already stored.

This line:

means:

Give me all the games currently saved.

Then:

games.forEach(function(game) {

creates HTML cards for those saved games.

There is one situation where you can get visual duplicates, though. If you call loadGames() multiple times without clearing #gameCollection, it will display another card for every game.

For example:

loadGames();
loadGames();

would show each game twice on the page, even though there's still only one copy in IndexedDB.

A good safeguard is to clear the display before loading:

function loadGames() {
  const transaction = db.transaction("games", "readonly");
  const store = transaction.objectStore("games");

  const request = store.getAll();

  request.onsuccess = function() {
    const games = request.result;

    // Clear existing cards first
    const collection = document.querySelector("#gameCollection");
    collection.innerHTML = "";

    games.forEach(function(game) {
      displayGame(game);
    });
  };
}

IndexedDB

Minecraft
Catan

Hades
Minecraft
Catan

So:

addGame()     → WRITES to database
loadGames()   → READS from database
displayGame() → creates HTML

Keeping those three jobs separate is a good way to think about your project.

means:

database.objectStoreNames.contains("games")

asks:

Does the database contain an object store called "games"?

It returns a boolean:

true   // "games" exists
false  // "games" does not exist

The ! operator means NOT. It reverses a boolean:

!true   // false
!false  // true

So:

if (!database.objectStoreNames.contains("games")) {
    // ...
}

means:

IF "games" does not already exist, run this code.

That's why we used:

if (!database.objectStoreNames.contains("games")) {
    database.createObjectStore("games", {
        keyPath: "id",
        autoIncrement: true
    });
}

In plain English:

"Check whether the games store already exists. If it doesn't, create it."

The ! is important because without it:

if (database.objectStoreNames.contains("games")) {
    database.createObjectStore("games");
}

you'd essentially be saying:

"If games already exists, try to create games."

Which is the opposite of what you want and would cause an error.
